# 数电发票识别改造实施计划

日期：2026-07-27

## 一、目标

把当前“通用解析加零散特殊处理”改造成：

1. 一个数电票共同基础模型。
2. 六个建立在共同基础上的独立类型扩展模型。
3. 三个整张票面明显不同的完整专用模型。
4. 红字、折扣、不征税等可叠加的共同状态模型。

本轮先覆盖当前 45 个真实样本。没有真实样本的 14 类票只登记边界，暂不开发识别能力。

## 二、最终结构

### 2.1 共同基础模型

负责所有普通数电票共有的内容：

- 发票号码和开票日期
- 普通发票或增值税专用发票
- 购买方和销售方
- 通用明细表
- 金额、税额、价税合计
- 开票人和备注原文
- 红字、负数和折扣状态

### 2.2 独立类型扩展模型

每个类型单独定义类型判定、专属字段、专属结构和专属校验：

- 建筑服务
- 成品油
- 货物运输服务
- 不动产经营租赁服务
- 旅客运输服务
- 通行费

### 2.3 完整专用模型

保留当前整张票面独立处理的模型：

- 机动车销售统一发票
- 航空运输电子客票行程单
- 铁路电子客票

## 三、执行顺序

## 第 0 步：建立真实样本验收基线

### 要做的事

当前项目没有发现现成的自动化测试目录，因此先补最小验收入口。

1. 固定当前 45 个真实样本清单。
2. 为每个文件记录：
   - 预期票面形态
   - 预期特定业务类型
   - 预期明细数量
   - 预期金额、税额和价税合计
   - 预期专属字段
   - 允许出现的真实缺失
3. 保存当前识别结果，作为改造前基线。
4. 建立一个可重复执行的真实样本验收脚本。

### 实现原则

- 不把真实发票复制进公开代码目录。
- 验收脚本从用户给定的样本文件夹读取。
- 使用 Python 标准库编写测试入口，不新增测试框架依赖。
- 每次修改后都运行同一批样本，防止修好一类又破坏另一类。

### 完成标准

- 样本数严格为 45。
- 每个文件都有唯一预期分类。
- 关键票面金额和明细数量有人工确认值。
- 当前成功、复核和失败结果形成可比较基线。

## 第 1 步：把“共同基础”和“类型差异”落实到项目结构

### 要做的事

1. 保留 `standard-invoice` 作为共同基础模型。
2. 为六种特定业务分别建立独立模型定义：
   - `building-service`
   - `refined-oil`
   - `freight-transport-service`
   - `real-estate-operating-lease`
   - `passenger-transport-service`
   - `toll-invoice`
3. 类型模型只声明与共同基础不同的部分，避免复制通用字段。
4. 让类型模型能够继承共同基础模型。
5. 在进入字段抽取前完成类型路由。

### 类型判定规则

按证据强度排序：

1. 票面内嵌结构化类型。
2. 票面左上角完整特定业务名称。
3. 该类型独有且完整的表头组合。
4. 票面标题和项目名称辅助确认。
5. 销售方名称只作弱证据，不能单独分类。

### 必须处理的边界

- 顺丰收派服务归入通用数电票，不能归入货物运输服务。
- 飞猪机票代订归入通用数电票，不能归入航空行程单。
- 挖机、水车和机械租赁归入通用数电票，不能归入不动产租赁。
- 普通蔬菜销售不能归入农产品收购发票。

### 完成标准

45 个样本的分类数量必须为：

| 模型 | 数量 |
|---|---:|
| 通用数电票 | 29 |
| 建筑服务 | 2 |
| 成品油 | 4 |
| 货物运输服务 | 1 |
| 不动产经营租赁 | 2 |
| 旅客运输服务 | 1 |
| 通行费 | 1 |
| 机动车销售统一发票 | 1 |
| 航空电子客票 | 2 |
| 铁路电子客票 | 2 |
| 合计 | 45 |

## 第 2 步：修复共同基础解析

这一步先解决所有类型共同遇到的根因。

### 2.1 合计区

#### 当前问题

标签定位失败时，程序按金额出现顺序猜测金额、税额和价税合计。

#### 改造方式

- 以“合计”“价税合计”“小写”为锚点。
- 使用同一视觉行和相邻区域确定字段归属。
- PDF 文本和 OCR 统一使用带页面位置的逻辑行。
- 删除会制造错误确定值的金额顺序回退。
- 无法确认字段时保留缺失和复核状态。

#### 验收样本

- 三张顺丰收派服务票
- 山西美嘉乐物业停车费票
- 海底捞餐饮票
- 高德打车旅客运输票

#### 完成标准

以顺丰 57.94 元样本为例，必须得到：

- 金额 54.66
- 税额 3.28
- 价税合计 57.94

不能再出现 57.94、54.66、3.28 三个字段循环错位。

### 2.2 购销双方

#### 当前问题

部分 PDF 的文字读取顺序与票面左右位置不同，购销双方可能互换。

#### 改造方式

- 先定位“购买方信息”和“销售方信息”区域。
- 在各自区域内提取名称和纳税人识别号。
- 坐标按页面宽高归一化。
- 文本顺序只作为补充证据。

#### 验收样本

- 京东现金折扣票
- 当前所有数电专票和普票

#### 完成标准

- 购买方和销售方不互换。
- 名称与纳税人识别号保持同一区域配对。

### 2.3 通用明细表

#### 当前问题

OCR 使用固定横坐标边界，PDF 文本又依赖文本块顺序，导致缩放后错列、多行名称断裂和明细丢失。

#### 改造方式

- 从当前页面的表头位置动态推导列边界。
- 坐标按页面宽度归一化。
- 按视觉行重建单元格。
- 支持项目名称跨行、规格型号跨行。
- 支持数量或单价为空的合法明细。
- 在找到“合计”区域后结束明细，不靠固定纵坐标。

#### 验收样本

- PNG 工业仪表图片票
- 京东现金折扣票
- 多行货物销售票
- 烟酒票
- 浩然物资 17 行明细票

#### 完成标准

- PNG 图片票保留票面全部 4 个明细项目。
- 京东票保留正数商品行和负数折扣行。
- 已成功的多行货物票不得减少明细。

### 2.4 折扣和红字状态

#### 改造方式

- 折扣作为负金额、负税额的独立明细行。
- 允许折扣行没有数量和单价。
- 折扣行与相邻项目建立关联，但不合并或删除。
- 红字状态保留被红冲蓝字号码、代码和确认单编号。
- 负数金额全程保持负号。

#### 验收样本

- 成品油现金折扣票
- 京东现金折扣票
- 易兴负数 1
- 易兴负数 2

#### 完成标准

- 两种不同票面的现金折扣都能识别。
- 两张红字票保持负数并保留关联号码。

## 第 3 步：逐类完成六个类型扩展模型

每个类型按相同顺序完成：

1. 类型判定。
2. 专属字段。
3. 专属结构。
4. 专属校验。
5. 真实样本验收。

### 3.1 建筑服务

保留当前正确的“建筑服务”类型标签，补齐：

- 建筑服务发生地
- 建筑项目名称
- 两个字段的完整性校验
- 建筑材料销售与建筑服务的边界

验收样本：2 个。

### 3.2 成品油

保留当前正确的“成品油”类型标签，补齐：

- 油品名称、规格、单位、数量
- 普通行与折扣行
- 红字和负数边界
- 成品油与普通商品销售的边界

验收样本：4 个。

### 3.3 货物运输服务

保留当前五列表处理，补齐：

- 货物运输服务类型判定
- 运输工具种类
- 运输工具牌号
- 起运地
- 到达地
- 运输货物名称
- 多行运输信息与明细的对应关系
- 收派服务、快递费与货物运输的边界

验收样本：1 个。

当前只有一个真实货运样本。先完成单行模型，多行货运不宣称已验证。

### 3.4 不动产经营租赁服务

新增：

- 产权证书或不动产权证号
- 面积单位
- 不动产地址
- 租赁开始日期和结束日期
- 跨地（市）标志
- 停车费与房租的共同模型
- 动产租赁排除规则

验收样本：2 个。

### 3.5 旅客运输服务

新增：

- 出行人
- 有效身份证件号
- 出行日期
- 出发地和到达地
- 等级
- 交通工具类型
- 网约车与航空、铁路、机票代订的边界

验收样本：1 个。

### 3.6 通行费

新增：

- 征税或不征税变体
- 车牌号
- 入口信息
- 出口信息
- 通行时间
- 停车费与通行费的边界

验收样本：1 个征税通行费。

当前没有不征税通行费真实样本。不征税变体只建立类型边界，不宣称已通过行为验收。

## 第 4 步：保护已有完整专用模型

### 要做的事

- 回归机动车销售统一发票 1 个样本。
- 回归航空行程单 2 个样本。
- 回归铁路电子客票 2 个样本。
- 确认新的共同基础和类型路由没有抢走这 5 个样本。

### 完成标准

- 五个样本仍进入原专用模型。
- 原有专属字段不减少。
- 航空民航发展基金、铁路行程和机动车车辆信息保持正确。

## 第 5 步：全量真实样本验收

### 验收维度

1. 类型是否正确。
2. 购销双方是否正确。
3. 明细数量是否正确。
4. 专属字段是否完整。
5. 金额勾稽是否正确。
6. 红字和折扣是否正确。
7. 状态是否真实。

### 状态判断

- 票面完整且结果正确：通过。
- 票面本身缺字段或证据冲突：需复核，并说明真实原因。
- 当前没有模型或文件无法处理：未建模或失败。

不能用默认值、金额顺序猜测或静默丢行把结果制造成“通过”。

### 必须通过的重点案例

| 案例 | 验收结果 |
|---|---|
| 三张顺丰收派服务票 | 通用数电票，金额勾稽正确 |
| 两张不动产租赁票 | 同一类型模型，专属字段完整 |
| 京东现金折扣票 | 正数行和负数折扣行完整 |
| 成品油现金折扣票 | 正数行和负数折扣行完整 |
| PNG 图片票 | 4 个明细项目完整 |
| 山西启达货运票 | 五项运输信息完整 |
| 高德打车票 | 旅客运输专属字段完整 |
| 山西交投通行费票 | 通行费类型及通行信息正确 |
| 两张建筑服务票 | 发生地和项目名称正确 |
| 航空、铁路、机动车 | 原有结果无回归 |

实际修改前会再次检查每个文件的调用关系。能在共同函数修复的问题只修一处，不在六个类型中重复打补丁。

## 五、提交批次

为了便于复核和回退，改造分成四个独立批次：

1. 类型继承、分类路由和分类测试。
2. 合计区、购销双方、动态明细和折扣状态。
3. 六个类型扩展模型及专属字段。
4. 45 个真实样本全量回归和结果整理。

每个批次必须通过对应真实样本后再进入下一批。某一批验证失败时保留真实错误并修复根因，不把失败积累到最后。

## 六、完成定义

本轮改造完成需要同时满足：

1. 45 个样本分类全部符合《数电发票分类与项目诊断》。
2. 当前四类已知失败的根因全部消除。
3. 六个特定业务都有独立类型模型。
4. 建筑和成品油类型标签继续正确。
5. 货运五列表能力继续保留并纳入完整模型。
6. 机动车、航空和铁路没有回归。
7. 页面缩放和图片分辨率变化不再依赖固定绝对像素。
8. 没有证据的字段保持缺失或复核，不生成猜测值。
9. 没有真实样本的类型不显示为已支持。
10. 输出台账中的状态和复核原因与真实识别结果一致。
